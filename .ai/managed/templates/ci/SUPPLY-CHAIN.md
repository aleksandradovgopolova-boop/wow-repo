# Supply-chain / OpenSSF: шаблоны CI, которые кит ставит дочке

Этот набор закрывает самый чистый пробел относительно практик GitHub и
[OpenSSF Scorecard](https://securityscorecards.dev/): цепочка поставок артефакта дочки —
зависимости, секреты, статический анализ, происхождение и содержимое релиза.

## Как это устроено: шаблоны, а не обязаловка

Кит **предлагает** эти файлы при `ai-ops init`/`update` и владеет ими так же, как остальными
child-workflow'ами (`ai-ops-*.yml`): он их поставил, отпечатал и обновляет свою нетронутую версию.
Дальше — ваше:

- **Опт-аут** любого файла — просто удалите его. Кит уважает удаление и не возвращает файл на
  следующем обновлении (как с `ai-ops-record.yml`).
- **Кастомизация** — правьте под свой стек (языки CodeQL, экосистемы Dependabot, пути артефактов).
  Кит не перезаписывает файл, который вы изменили.
- **Присутствие и сила** этих проверок видны в governance-отчёте (см. `engineering-standard-requirements.md`,
  SR-17..20): отчёт читает состояние child-workflow'ов, не заводя второй джобы того же смысла.

## Граница с инвариантом кита

Инвариант «никаких новых рантайм-зависимостей у инструментов кита» (stdlib + pyyaml) относится к
**коду движка**. Здесь — **фордж-конфигурация вашего репозитория**: GitHub-нативные механизмы
(Dependabot, CodeQL, Scorecard, аттестации Sigstore) и портируемые инструменты сборки. Кода кита и
его зависимостей они не касаются.

## Advisory по умолчанию, блокирующим — по решению

Ни одна из этих проверок **не роняет ваш PR по умолчанию** — это осознанно:

- у кита объявлен бюджет блокирующих гейтов (не больше восьми), и набор не имеет права добавить
  девятый молча;
- блокирующей проверку делаем **только с нулём ложных** — секрет-сканеры и SAST шумят на фикстурах
  и примерах, пока не настроен allowlist.

Как ужесточить, когда готовы:

| Проверка | Сделать блокирующей |
|---|---|
| CodeQL (`ai-ops-codeql.yml`) | включить code scanning как required check в Branch protection |
| Secret scan (`ai-ops-secret-scan.yml`) | убрать `continue-on-error: true` после обнуления ложных |
| Scorecard (`ai-ops-scorecard.yml`) | оставить ориентиром; порог балла обсуждается, а не гейтит |

## Что нельзя поставить файлом: настройки репозитория

Два пункта — это **настройки**, а не workflow. Кит их называет, включаете вы:

1. **Secret Scanning + Push Protection** — Settings → Code security → включить *Secret scanning* и
   *Push protection*. Push protection блокирует пуш с секретом **до** попадания в историю (нативно;
   публичным репозиториям бесплатно, приватным нужен GitHub Advanced Security). Портируемый бэкстоп
   на gitleaks кит ставит файлом (`ai-ops-secret-scan.yml`), но он ловит уже закоммиченное — не
   заменяет push protection, а дополняет.
2. **Branch protection** — Settings → Branches: защитить `main`, потребовать PR и прохождение
   нужных проверок. Именно здесь advisory-проверка становится обязательной.

## Pinned-Dependencies: закрепление на commit SHA

OpenSSF Pinned-Dependencies засчитывается, когда действия в workflow'ах закреплены на **commit SHA**,
а не на тег: тег `@v4` можно молча передвинуть на скомпрометированный коммит, SHA — нет.

В поставляемых шаблонах действия закреплены по **мажорному тегу** — сознательно: подставить SHA,
который нельзя проверить в момент написания, значит поставить дочке заведомо ломкий или ложный пин.
Правильный путь к SHA-пинам:

1. Закрепите действия на SHA (например: `actions/checkout@<40-символьный-sha> # v4.2.2`).
2. `dependabot.yml` с экосистемой `github-actions` (в наборе) будет двигать **сам SHA**, оставляя в
   PR комментарий с версией. Так «закреплено на SHA» перестаёт означать «навсегда устарело».

Особенно это важно в workflow'ах сборки и релиза (`ai-ops-sbom.yml`) — там компрометация действия
подменяет подписываемый артефакт.
