# SessionEconomyPolicy — гигиена сессий и бюджет контекста (v3.16.0)

## Зачем

Главный источник неэффективности — не «модель много пишет», а **недели работы в одной огромной
сессии**, где каждый запрос заново оплачивает перечитывание нерелевантной истории. AI Ops должен не
постфактум сказать «ты потратила много», а **вовремя остановить плохой паттерн и дать конкретную
команду**: продолжать, сделать compact, начать новую задачу (`/clear`) или новую сессию.

Правило по умолчанию:

```
одна самостоятельная задача → одна сессия
```

Исключение — логическое продолжение того же WorkItem.

## Пороги (стартовые, калибруются)

| Состояние                 | Контекст  | Поведение кита |
|---------------------------|-----------|----------------|
| normal                    | до 150k   | работа продолжается |
| attention                 | 150–250k  | кит оценивает оставшийся объём |
| compact_recommended       | 250–400k  | завершить логический кусок и сделать `/compact` |
| new_session_recommended   | > 400k    | не начинать новый блок работы в этой сессии |

Числа — не вечные константы, а стартовая политика. Настраиваются в `.ai-ops.yaml`:

```yaml
session_economy:
  target_context_tokens: 150000
  compact_recommended_at: 250000
  new_session_recommended_at: 400000
  one_task_per_session: true
  allow_cross_task_session: false
  session_token_budget: 20000000     # потолок расхода ВСЕЙ сессии, не одного прогона
```

## Откуда берётся число (и почему это важно)

Расход **измеряется** по транскрипту живой сессии Claude Code
(`~/.claude/projects/<slug>/<session_id>.jsonl`): `context_current` — сумма
`input_tokens + cache_read_input_tokens + cache_creation_input_tokens` последнего хода, то есть
ровно то, что модель фактически прочитала. Статус — `measured`.

Если транскрипт не найден, кит говорит **почему именно** («нет каталога сессий для этого пути»,
«не задан id сессии») и оставляет `unavailable` — не 0 и не «норма». Правильное «не знаю»,
выданное по неизвестной причине, чинить нечем.

Читаются ТОЛЬКО метаданные: числа, timestamps, id, рабочий каталог. Содержимое промптов и ответов
не читается никогда — это проверяется тестом, а не обещается.

До 2026-08-13 всё это было объявлено и мертво: провайдер искал транскрипт по несуществующему пути
`.../sessions/<id>.jsonl`, контекст всегда оставался `unknown`, и ни один из четырёх исходов на
живой работе не наступал.

## Потолок сессии ≠ потолок прогона

`engine/budget.py` ограничивает ПРОГОН (`max_model_calls`, `max_cost`), `economic_preflight` и
usage-ledger считают вызовы моделей самого кита. Ни один из них не видит главный источник расхода:
сессию, которая живёт неделями и на каждом ходе заново оплачивает перечитывание истории.

`session_token_budget` закрывает именно это — суммарные токены всех ходов сессии, включая
кэш-чтения (они и есть плата за перечитывание). Порог сработает даже когда контекст выглядит
нормально: замер на настоящем транскрипте — сессия с 18.07 по 04.08 прочитала 2.9 млрд токенов
при «нормальном» контексте 405k после девяти компакций.

Enforcement тот же — **advise**: сильный совет с точной командой, не блокировка.

## Enforcement — СИЛЬНЫЙ СОВЕТ, не блок

Кит **НЕ управляет** рантаймом Claude Code и не может сам выполнить `/clear`/`/compact`/`/exit`. Он
даёт **сильную рекомендацию с точной командой** и причиной; решение и выполнение — за владельцем.
Кит **не блокирует** прогон движка из-за тяжёлой сессии (решение владельца: advise, не block).

Кит **не прерывает** посреди применения миграции или незавершённого commit. На небезопасной границе
рекомендация — `defer`: дождаться безопасной точки, затем перезапросить.

## Четыре исхода (SessionRecommendation)

1. **continue** — тот же WorkItem, контекст лёгкий, следующий шаг переиспользует собранное. Команды нет.
2. **compact** — задача не завершена, контекст нужен, но уже дорогой, логическая часть закрыта →
   `/compact <что сохранить / что удалить>`.
3. **clear** — предыдущая задача закрыта, следующая независима, тот же репозиторий, handoff сохранён →
   `/clear <WID>-completed` затем `ai-ops do "<next>"`.
4. **new_session** — большой этап закончен / сессия слишком тяжёлая / риск продолжить старый разговор →
   `/exit` → `cd <repo> && claude` → `ai-ops do "<next>"`.

## Порядок приоритетов (что экономить в первую очередь)

```
1. Гигиена сессии и контекста   (не таскать 800k истории на каждом запросе)
2. Делегирование разведки        (см. WP4, срез 2)
3. Ограничение бесполезных итераций
4. Выбор runtime
5. Effort и краткость ответа
```

Кит не должен экономить копейки на output, продолжая перечитывать огромную историю.

## Расход называется ДО траты, а не только после

Ритуал завершения WorkItem выдаёт рекомендацию в конце — этого мало: решение «здесь новую сессию не
начинаем» принимается ДО работы. Поэтому перед каждым прогоном кит называет расход и состояние
сессии (`_session_guard_before_start` -> `presenter.from_session_economy`), причём **на любом
исходе**, включая «менять сессию не нужно». Молчание неотличимо от «всё в порядке», а раньше страж
молчал в 100% прогонов: он печатал что-либо только на исходах `new_session`/`compact`, которые при
`unknown`-контексте не наступали никогда.

## Task Completion Ritual (обязателен)

После каждого завершённого WorkItem кит проверяет: результат достигнут → проверки пройдены →
состояние сохранено → handoff создан → решения записаны → commit/PR зафиксированы → usage посчитан —
и **обязательно** выдаёт SessionRecommendation с точной командой. Без этого задача не считается
полностью закрытой с точки зрения AI Ops, даже если код готов. См. `tools/session_guardrails.py`
(`completion_ritual`) и снимок `tools/session_telemetry.py`.

Пункт «handoff создан» **выводится из наличия файла**, а не объявляется (17.08.2026). До этого он был
значением параметра по умолчанию: `ai-ops session` на живой сессии печатал «handoff_created» при
полном отсутствии сессионного handoff в природе, и рекомендация уйти в новую сессию утверждала
«Handoff/решения сохранены в репозитории». Ритуал, проверяющий честность закрытия работы, имел
пункт, неопровержимый по построению. Теперь неизвестность отличается от отрицания: «handoff НЕ
сохранён» и «проверить нечем — путь репозитория не передан» — разные ответы.

## SessionHandoff — состояние для СЛЕДУЮЩЕЙ сессии

`SESSION COMPLETE` с разделами Goal / Done / Decisions / Changed / Tests / Open / Next / Risks.
Механизм — `tools/session_handoff.py`; файл — `.ai/runtime/sessions/<session_id>/handoff.yaml`.

Разделы названы **именами `RunHandoff`** (`engine/run_handoff.py`) дословно, потому что тот уже несёт
те же семь полей: дублировать словарь значило бы развести две правды об одном. Разный только предмет:

| | `RunHandoff` | `SessionHandoff` |
|---|---|---|
| предмет | один прогон движка по одному WorkItem | рабочий контекст сессии целиком |
| где | `features/<wid>/run-handoff.yaml` | `.ai/runtime/sessions/<sid>/handoff.yaml` |
| читает | `resume` | следующая сессия |
| видит правки не через движок | нет | да |

Замер, из которого видно, что одного `RunHandoff` мало: в сессии кита 17.08.2026 было 329 ходов,
движок не звался ни разу, `features/` пуст — весь труд сессии не имел носителя вообще.

Пишется, когда рекомендация советует сменить сессию (`new_session`/`clear`): готовить переход там,
где никто никуда не уходит, значило бы заводить файл ради файла. `goal` **не выводится из кода** —
цель знает тот, кто её ставил; вывести её из диффа значило бы пересказать сделанное и назвать это
замыслом. Не передали — раздел честно пуст со словами «не названа».

Предел объявлен здесь, а не обнаружен потом: `.ai/runtime/` в `.gitignore`, поэтому handoff **не
переезжает на другую машину**. Это состояние одной машины, как и остальное в `.ai/runtime/`; решение
о коммите — за владельцем (`planning/plan.yaml`, `session-protocol-owner-decisions`).

## Инструменты

- `ai-ops session` — снимок телеметрии + рекомендация по текущей границе.
- `tools/session_telemetry.py` — машинный снимок (объём/стоимость/контекст, честный usage_status).
- `tools/session_guardrails.py` — политика/классификация/рекомендация/ритуал.
- `tools/session_handoff.py` — SESSION COMPLETE: сборка, запись, поиск последнего handoff сессии.

## Чего этот документ НЕ решает

Кит говорит о лимите сессии только на путях `do` / `run --execute` и в конце прогона движка. Обычная
рабочая сессия — разбор, правки, ревью — не проходит ни через один, и молчание там означает «не
спросили», а не «норма». Это открытая работа `session-watch-speaks-unasked`, а не свойство политики.
