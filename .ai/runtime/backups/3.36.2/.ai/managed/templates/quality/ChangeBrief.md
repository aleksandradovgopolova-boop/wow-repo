# Change Brief (v3.8.3)

Обязательный блок ДО кода (в задаче или PR). Цель — сформулировать инвариант и перечислить ВСЕ
затронутые сквозные пути ДО реализации, а не осознать их постфактум. Занимает несколько минут.
Правило: не писать код, пока не перечислены все затронутые runtime-пути.

```text
Результат:
Что должно реально заработать для пользователя.

Затрагиваемые пути:
Какие runtime-сценарии/швы меняются (перечислить ВСЕ — это и есть главная защита).

Инварианты:
Что нельзя нарушить.

Основные failure modes:
Максимум пять.

Доказательство:
Какие проверки подтвердят результат — включая три обязательных теста capability:
  1. positive — механизм делает действие;
  2. fail-closed — сбой НЕ становится зелёным результатом;
  3. side-effect proof — действие ДЕЙСТВИТЕЛЬНО произошло (доказать ПРЕЖДЕ проверки реакции гейта).

Не входит:
Что сознательно НЕ делаем в этом изменении.
```

## Пример (задним числом — parallel trust wiring)

Если бы Change Brief составлялся до rc2, «Затрагиваемые пути» сразу перечислили бы:

```text
package scope · shared contracts · clone identity · fan-in · integration SHA ·
security approval · delivery transaction · provider failure · cleanup
```

— и большинство последующих фиксов (scope-enforcement, clone identity в реальных клонах,
кросс-платформенность git-идентичности) вошли бы в первый PR, а не в три итерации.

## Когда обязателен side-effect proof

Всегда, но особенно для гейтов, которые ЧТО-ТО блокируют по факту изменения (scope, security,
regression). Тест обязан сперва доказать сам факт изменения, иначе гейт «проходит» на пустом
диффе — ложный зелёный. Для кода, зависящего от Git/FS/сети/ОС/внешнего CLI, добавляется
environment-тест (напр. `GIT_CONFIG_GLOBAL=/dev/null` для симуляции CI-раннера без идентичности +
нативный smoke на macOS).
